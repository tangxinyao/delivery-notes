## 0. 三条贯穿性判据

先问这三个问题，八成的选型就定了：

| 问题 | 决定什么 | 分叉 |
| --- | --- | --- |
| **① 数据能不能出域？** | **推理引擎** | 不能 → 私有化部署（vLLM / SGLang / llama.cpp）；能 → 托管 API |
| **② 有没有免费的自动 verifier？** | **Benchmark 的评委构成** | 有（能跑测试、能比对末态）→ 脚本为主；没有 → 模型评委 + 人类 golden set |
| **③ 动作可不可逆？** | **Agent 架构与人机边界** | 可逆（改文件、查询）→ 可放开自主度；不可逆（发邮件、下单、改生产配置）→ 计划先行 + 人工闸门 |

## 1. 总览矩阵

| FDE 场景 | 首要 Benchmark 指标 | 评委来源 | 推理引擎 | Agent 架构 | 部署位置 |
| --- | --- | --- | --- | --- | --- |
| **研报 / 文档问答**（Morgan Stanley 型） | recall@k、nDCG@k、引用准确率、幻觉率 | 脚本（引用可溯）+ 专家 golden set | **SGLang**（前缀复用）或私有 vLLM | 轻量 ReAct 或纯 RAG pipeline（未必需要 agent） | 私有云 |
| **合规 / 风控审查**（金融） | **pass^k**、假阴性率、审计可追溯性 | 人类专家为主 + 脚本硬门槛 | 私有化 vLLM | **Plan-and-Execute**（计划可审计） | 本地 / 私有云 |
| **欺诈检测**（按揭、交易） | precision/recall、误报成本、延迟 | 脚本（有标签真值） | vLLM（高吞吐批量） | 非 agent —— 模型 + 规则引擎 | 私有云 |
| **战场 / 情报态势**（Maven 型） | TSR、TTFT、**离线可用性** | 人类操作员 + 脚本 | **llama.cpp**（边缘/断网）+ NPU | ReAct（人在环，每步可否决） | **纯本地 / 边缘** |
| **装备维护 / 预测性维保**（GE Aerospace 型） | 预测准确率、召回、业务指标（产出提升） | 脚本 + 业务 A/B | 边缘 llama.cpp + 云端 vLLM | Plan-and-Execute（维保排程） | 边缘 + 云 |
| **临床 / 科研 copilot**（医疗） | **幻觉率（最优先）**、引用准确率、CSAT | **人类临床专家为主** | 本地 vLLM / llama.cpp | ReAct + **强人在环** | 本地 |
| **制造 MES / 生产健康度** | 端到端延迟、告警准确率、OEE 等业务指标 | 脚本 + 业务指标 | 边缘推理 + 云端聚合 | Graph-based 编排（流程固定、要 checkpoint） | 边缘 + 云 |
| **能源作业优化**（BP / Jacobs 型） | **业务结果指标**（省电 %、成本）而非模型指标 | 脚本 + 现场验证 | 云端 vLLM（非实时） | Plan-and-Execute / 优化求解 + LLM 解释层 | 云 |
| **流程自动化 / 单据处理**（10Clouds 型） | **TSR、cost per task、处理时长、步骤数** | 脚本（结构化抽取有真值）+ 抽样人工 | vLLM（批量高并发） | **ReWOO / LLMCompiler**（流程固定、可并行） | 云 |
| **客服 / 工单** | **containment rate、pass^k、CSAT、TTFT** | 模型评委规模化 + 人类抽样 | **SGLang**（多轮共享前缀） | Handoff-based（意图路由 + 转人工） | 云 |
| **内部 coding agent 交付** | **pass@k / pass^k、SWE-bench 类、PR 通过率** | **脚本（单测、CI）—— 唯一有免费 verifier 的场景** | 托管 API 或私有 vLLM | Coding agent（Claude Code / Cursor）+ subagent | Local（敏感）/ Cloud（长时批处理） |
| **CoWork / 跨 SaaS 编排** | TSR、**轨迹效率、冗余率**、误操作率 | 模型评委 + 人类（**无免费 verifier**） | 托管 API | Graph-based + MCP 工具层 + **不可逆动作人工确认** | 云 |

## 2. 逐场景展开（挑关键的四类）

### 2.1 研报 / 知识问答 —— Morgan Stanley 型

**场景**：把内部研究成果交到一线业务手里。FDE 实践的奠基案例，6–8 周交付管线。[04 §2.2]

- **Benchmark**：这是**检索问题伪装成生成问题**。先测 `recall@k`（相关 chunk 有没有进 top-k）—— 召不回来，后面再好的模型也救不了；再测 `nDCG@k`（排序质量）；最后才测生成侧的引用准确率与幻觉率。
- **评委**：引用能否溯源可以**脚本判定**；"答得好不好"必须**领域专家 golden set**（100–300 条真实问题）。模型评委用来做回归大盘。
- **引擎**：同一份知识库反复被检索 → **前缀高度共享** → **SGLang 的 RadixAttention 正对口**（共享上下文场景比 vLLM 高 ~29% 吞吐 [02 §1.3]）。
- **Agent**：**多数情况不需要 agent**。固定 RAG pipeline + 至多一层 ReAct 做查询改写。上 agent 只会增加不确定性而不增加准确率。
- **坑**：Morgan Stanley 案例的技术难点是 retrieval tuning，不是模型选型 —— 这个教训到 2026 年依然成立。

### 2.2 国防 / 边缘情报 —— Maven 型

- **Benchmark**：**TTFT 与离线可用性权重高于绝对准确率**。加测断网、降级、低电量下的表现。
- **评委**：人类操作员为唯一权威；脚本做硬性安全门槛。
- **引擎**：**llama.cpp**（零依赖、可移植、单流 TTFT 最快 8–12ms [02 §1.2]）+ NPU 做 prefill（Snapdragon X Elite NPU prefill 是 CPU 的 18.1× [02 §1.6]）。这是 llama.cpp 而非 vLLM 唯一明确胜出的生产场景。
- **Agent**：ReAct，**每一步都可被人否决**。绝不用 ReWOO —— 战场环境变化快，不看反馈的计划必然失效 [03 §1.2]。

### 2.3 流程自动化 / 单据处理 —— 10Clouds 型

**场景**：8 个 bot，处理时长 −57%，单件 30 分钟 → 13 分钟 [04 §2.6]

- **Benchmark**：客户只认**业务指标** —— 处理时长、步骤数、屏幕切换数。模型指标是内部调优用的。必须在**同一批真实单据**上做前后对比。
- **评委**：结构化抽取有真值 → **脚本为主**，人工抽样校准。这是三类评委里最省钱的一档。
- **引擎**：批量、高并发、可离线跑 → **vLLM**（50 并发 920 tok/s [02 §1.1]）。
- **Agent**：流程固定、步骤间依赖已知 → **ReWOO**（计划里写死工具与参数，消除观察依赖的重复调用 [03 §1.1]）或 **LLMCompiler**（DAG 并行，原论文称 3.6× 加速）。**这是 ReAct 最不该用的场景** —— 每步一次 LLM 调用纯属浪费。

### 2.4 客服 / 工单

- **Benchmark**：**containment rate**（无需转人工完成的比例）是客户最认的一个数；`pass^k` 保证一致性；TTFT 决定体感；CSAT 做长期追踪（>4.2 强，<3.5 说明用户在忍受 [01 §1.5]）。
- **评委**：量大 → **模型评委规模化打分**（pairwise，一致率可达 ~85% [01 §2.2]），人类做抽样与争议裁决。
- **引擎**：多轮对话，system prompt + 历史高度共享 → **SGLang**。
- **Agent**：**Handoff-based**（OpenAI Agents SDK 风格）—— 意图路由 + 干净的转人工路径。
- **警示**：τ-bench 的 retail 域 **pass^8 < 25%** [01 §1.1] 就是客服场景的真实写照。上线前必须按 `pass^k` 而非 `pass@k` 验收。

## 3. 反模式清单

| 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 用 Ollama 做生产 API | 并发下崩到 41 tok/s、P99 673ms [02 §1.1] | vLLM 或 SGLang |
| 多 GPU 上跑 llama.cpp | 不做张量并行，白买卡 [02 §1.4] | vLLM / ExLlamaV2 |
| 固定流程上用 ReAct | 每个 action 一次 LLM 调用，成本与延迟线性累积 [03 §1.2] | ReWOO / LLMCompiler |
| 变化环境里用 ReWOO | 计划不看反馈，环境一变全盘皆错 [03 §1.2] | ReAct / Plan-and-Execute |
| 用 `pass@k` 向客户汇报 | 测的是能力上限，不是可靠性 | `pass^k` |
| 只用脚本评"答得好不好" | 程序化检查**判断不了**有用、好、合调性 [01 §2.1] | 叠加模型评委 + 人类 golden set |
| 检索问题上狂换模型 | 召不回来换什么模型都没用 | 先修 recall@k |
| 给不可逆动作全自主权 | 发错邮件、下错单无法回滚 | 计划先行 + 人工闸门 |
| 让模型掌管顶层控制流 | 顶层循环属于确定性代码，模型只在一次迭代内被调用 [07 §3.2] | 控制流写进代码 |
| 把业务规则写进 prompt | 无法审计、无法复用、改一条要重测全部 [07 §2.3] | 规则建模进本体或确定性代码 |
| 先定 rubric 再去打分 | criteria drift —— 标准依赖于观察到的输出 [07 §1.1] | 带着真实输出去见专家，边看边定 |
| 拿公开榜单当验收标准 | 客户场景与榜单分布无关 | 客户场景内 golden set（100–300 条） |

## 4. 一张交付验收清单（可直接抄进 SOW）

1. **数据边界**已确认，推理引擎选型与之匹配，并有压测数据（并发数 × 吞吐 × P99）
2. **Golden set** 已与客户共同标注，规模 ≥100 条，覆盖长尾
3. 验收指标含 **`pass^k`**（k 按客户容忍度定，一般 k=5 或 8）而非仅 `pass@k`
4. 有 **TTFT / cost-per-task** 的基线与目标
5. 所有**不可逆动作**都有人工闸门或可回滚路径
6. **轨迹可观测**（不只是日志）—— 出问题能定位到哪一步、用了哪个工具
7. **交接完成**：客户内部有人能独立运维、能改 prompt、能重跑 eval
   —— Palantir playbook：**交接不是附录，交接就是验收标准** [04 §4]
